# ClaimsDock — build CLAUDE.md

## What this is

Build-process instructions for ClaimsDock, a medical-claims adjudication copilot prototype (embedded assistant: Anchor). All domain logic — enums, taxonomies, router actions, confidence/severity/status rules, recommendation logic, reseed mechanics — lives in `project-spec.txt`, not here. This file governs how the app gets built, not what it is. If the two ever seem to disagree, `project-spec.txt` is the domain authority; this file is only ever wrong about process.

## Stack

- See `AGENTS.md` (generated by the Next.js scaffold tool) for version-specific agent guidance about this Next.js release — its conventions may differ from training data.
- Next.js (App Router), TypeScript
- Hosted on Vercel; developed and verified locally first, every phase
- Single Anthropic API key, server-side only (`ANTHROPIC_API_KEY`, never exposed to the client) — same discipline as the AUGUR build
- No database. Pipeline output generated and cached per ISO week server-side; adjuster actions (approvals, overrides, audit log) persisted client-side via localStorage — see project-spec.txt Sections 1 and 11 for why

## File structure — separation of concerns

- `app/` — Next.js routes and pages. No business logic beyond wiring.
- `app/api/` — server routes: pipeline run, router/Anchor query, embeddings/retrieval
- `lib/claims/` — claims schema, seed generator (ISO-week-seeded)
- `lib/rules/` — deterministic calculation functions: severity, SLA/deadline math, coverage math, category+confidence → action lookup. Pure functions, no API calls, unit-tested.
- `lib/pipeline/` — the 2-call batched Evaluation Pipeline (Analysis; Confidence+Recommendation)
- `lib/router/` — Interactive Router tool-use definitions + dispatch (the 4 tools)
- `lib/rag/` — corpus chunking, embedding, in-memory vector store, retrieval
- `content/corpora/` — the three authored reference documents (coverage policy, fraud-indicator, deadline reference)
- `components/` — UI components (React + one `.module.css` per component; Phases 8A/8B done — see Build phases below)
- No inline styles or scripts now that a real UI exists — see Style Rules below

Do not mix or misattribute concerns to the wrong layer (a lesson carried over from both prior builds' file-structure discipline).

## Style rules

Three styles — Ledger, Clinical, Field — each in light and dark (six combinations total), driven entirely by CSS custom-property tokens in `src/app/tokens.css`, scoped via `[data-style]`/`[data-theme]` attributes on `<html>`. Component CSS reads only semantic tokens (`--accent`, `--ink-primary`, `--radius-md`, `--status-critical-text`, etc.), never a hardcoded hex or a one-off per-style branch — adding a style or mode means adding one token block, not touching component code.

- One `.module.css` per component; no inline styles or scripts.
- Every component's hover/focus/active states get one consistent treatment across all its kinds/variants — never three different looks for what's conceptually one interaction.
- Icons are plain inline `currentColor` SVGs, no icon library — every icon recolors correctly with its parent badge/text color across all six style/mode combinations without a separate dark-mode asset.
- A handful of hover-specific tokens (`--button-primary-hover-bg` and similar) exist alongside the semantic ones, for the cases — hand-picked per-style hover colors — that don't reduce to a formula against an existing token.
- Badge/button/checkbox icon assets live in `assets/`, traced from the real Figma component sets directly rather than approximated, wherever the asset actually exists.
