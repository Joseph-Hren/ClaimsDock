# ClaimsDock — build CLAUDE.md

## What this is

Build-process instructions for ClaimsDock, a medical-claims adjudication copilot prototype (embedded assistant: Anchor). All domain logic — enums, taxonomies, router actions, confidence/severity/status rules, recommendation logic, reseed mechanics — lives in `project-spec.txt`, not here. This file governs how the app gets built, not what it is. If the two ever seem to disagree, `project-spec.txt` is the domain authority; this file is only ever wrong about process.

## Stack

- See `AGENTS.md` (generated by the Next.js scaffold tool) for version-specific agent guidance about this Next.js release — its conventions may differ from training data.
- Next.js (App Router), TypeScript
- Hosted on Vercel; developed and verified locally first, every phase
- Single Anthropic API key, server-side only (`ANTHROPIC_API_KEY`, never exposed to the client) — same discipline as the AUGUR build
- No database. Pipeline output generated and cached per ISO week server-side; adjuster actions (approvals, overrides, audit log) persisted client-side via localStorage — see project-spec.txt Sections 1 and 11 for why

## File structure — separation of concerns

- `app/` — Next.js routes and pages. No business logic beyond wiring.
- `app/api/` — server routes: pipeline run, router/Anchor query, embeddings/retrieval
- `lib/claims/` — claims schema, seed generator (ISO-week-seeded)
- `lib/rules/` — deterministic calculation functions: severity, SLA/deadline math, coverage math, category+confidence → action lookup. Pure functions, no API calls, unit-tested.
- `lib/pipeline/` — the 2-call batched Evaluation Pipeline (Analysis; Confidence+Recommendation)
- `lib/router/` — Interactive Router tool-use definitions + dispatch (the 4 tools)
- `lib/rag/` — corpus chunking, embedding, in-memory vector store, retrieval
- `content/corpora/` — the three authored reference documents (coverage policy, fraud-indicator, deadline reference)
- `components/` — UI components (populated once Figma design exists)
- No inline styles or scripts once a real UI exists; styling conventions TBD — see Style Rules below

Do not mix or misattribute concerns to the wrong layer (a lesson carried over from both prior builds' file-structure discipline).

## Build phases

Numbered for tracking, not necessarily 1:1 with individual sessions — the actual session-by-session record lives in `build-log.html`.

1. Claims schema + seed generator — 20-claim test set (Section 10), ISO-week-seeded relative dates
2. Author the three RAG corpora — condensed, medical-claims-scoped, real sources cited
3. Deterministic calculation layer — severity, SLA math, coverage math, action-lookup tables — unit tested before any model call is wired in
4. RAG retrieval layer — chunk + embed corpora, in-memory similarity search (embedding provider TBD — see Open Questions; walk through together when this phase starts, first time doing this)
5. Evaluation Pipeline — 2 batched API calls (Analysis; Confidence + Recommendation) — see project-spec.txt Section 1 implementation note
6. Interactive Router + Anchor — tool-use dispatch across the 4 tools, grounded via the retrieval layer
7. Human gate + persistence — approve/deny/escalate/edit actions, audit log, localStorage
8. Placeholder UI — plain/minimal worklist + card views to verify phases 1–7 end to end before real design exists
9. Real UI — wired in once Figma design lands (built in a separate thread); replaces phase 8
10. Workflow visualization — standalone Artifact (D3-based diagram of the full system: pipeline, router, human gate, confidence/severity/status logic, category taxonomies). Can be built any time in parallel, not gated on any phase above — good as an early architecture sanity-check too.
11. 100+ claim scale-up — batching strategy for the production-scale claim set, deferred until phases 1–9 are proven at 20-claim scale

The actual session-by-session record lives in `build-log/build-log.html`, not restated here.

## Deployment

- Local dev and testing first, for every phase
- Vercel deploy once a phase is stable locally
- Env vars set in Vercel project settings, never committed
- Serverless functions are stateless between invocations — nothing here depends on writing to disk in production (see persistence model in project-spec.txt)

## Out of scope

Full list and rationale lives in project-spec.txt's "Explicit Non-Goals" section — repeated here briefly as a build boundary:

- No RBAC / role-based access, no member-facing view — adjuster-only, single view
- No real billing/reimbursement integration — status change + audit log is the simulation of that handoff
- No real document upload/OCR — a missing-information hold is a data-field state, not a file
- No hosted vector database — in-memory retrieval only, at this corpus size
- No full observability stack — a few trace markers, not Phoenix-grade tooling

## Build log

Every build session gets logged in its own folder, `build-log/` (`build-log/build-log.html` + `build-log/build-log.css`), kept separate from application files. Follows the structural pattern of the previous projects' logs in `previous-projects/` — masthead, highlights, session-by-session milestones with exhibits, a status table, a prompt-version log where relevant.

Update it:

- **Always**, after a major change or a completed build phase — finishing one of the numbered phases above, a significant design decision, a real bug worth documenting.
- **At your judgment**, after smaller additions — err toward logging more rather than less. The entire point of this project is the documentation of the process, not just the finished artifact, so the log deserves the same care AUGUR and VDBP's did.
- Treat it as a living document updated alongside the build, not reconstructed from memory afterward.

## Process

Efficiency, planning-before-executing, and token-conscious builds are already governed by the root-level CLAUDE.md — that discipline applies here without needing to be restated. Ask clarifying questions before any build pass with more than one reasonable approach; this project's whole value is in decisions made deliberately, not defaulted into.
