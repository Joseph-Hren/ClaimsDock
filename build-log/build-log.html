ClaimsDock

A medical-claims adjudication copilot: an automatic evaluation pipeline that reads incoming claims for evidence, fraud indicators, and coverage math, paired with an on-demand router and an embedded grounded-assistant panel (Anchor) for the adjuster to ask questions of. Every recommendation traces to a real source document; nothing becomes a real action without a human's approval. This page tracks the build as it happens, starting before any code exists.

What this is

Most claims should never need a human at all. ClaimsDock's core thesis: a router that decides what a plain-language question actually needs, grounding so every recommendation traces to a real policy line rather than an invented one, honest uncertainty tagged with a reason rather than a bare confidence score, and a human gate so nothing becomes a real action without explicit approval. Applied here to medical claims specifically — a domain that sits at the intersection of health, insurance, and finance — but the same skeleton could re-skin for other operational review work.

The functional spec (project-spec.txt) was written and revised before any code — architecture, taxonomies, and rules first, interface second. That document is the domain authority; this log tracks the build against it.

  1. Architecture & build-process planning

    Done

    project-spec.txt · CLAUDE.md

    Before any code: read the full functional spec end to end and worked through what it left open. Settled the evaluation pipeline down to two batched API calls total per run (not one call per claim, not three per claim) by moving severity, status, and the category-to-action mapping out of the model's hands entirely and into deterministic code — the spec was already explicit that those are calculations, not judgment calls, so the pipeline redesign just followed that logic all the way through. Confirmed the router as a real tool-use judgment step, not string-matching. Chose real chunked-embedding retrieval over full-context stuffing for the three RAG corpora specifically so the project demonstrates actual retrieval mechanics, not a shortcut past them — scoped to an in-memory vector store rather than a hosted database, since the corpora are small by design. Resolved a real multi-user question along the way: pipeline output (evidence, confidence, recommendation) is cached per ISO week and shared, since it depends only on claim data; adjuster actions are private, client-side, per browser — which is also what guarantees a new visitor always sees the full, untouched queue.

    All of this is now written into project-spec.txt (amended in place, with each decision dated inline) and a new CLAUDE.md that sets the stack, file structure, and the 11-phase build order below. Two open items carried forward on purpose rather than forced to a premature decision: which embedding provider to use for retrieval (a local, self-hosted model vs. Voyage AI), and the batching strategy once the claim set grows past 20 toward a production-scale ~100+.

  2. Claims schema & seed generator

    Done

    src/lib/claims/ · scripts/validate-claims.ts

    Repo scaffolded (Next.js 16, TypeScript, App Router) and pushed to GitHub. On top of it: a full claim schema (types.ts) with genuinely separate CMS-1500 and UB-04 shapes, field names mirroring the real box numbers rather than generic ones, and 20 authored claim records covering all 15 scenarios from the spec's test-set design — exactly 4 clean, 3 ambiguous, 3 missing-data, 3 complex-coverage-math, and 7 fraudulent, including the linked professional/facility pairs and the documentation-mismatch pattern that only shows up by comparing two linked claims against each other.

    Content was authored for domain plausibility, not just schema conformance: age- and sex-appropriate procedures, diagnosis/procedure pairings that read as a real encounter rather than a random field-filler, and a shared provider identity reused across three of the fraud claims to produce the volume-spike pattern — which needed its own small dataset (provider-history.json) stating a trailing 6-month average against a current-month count, since "3.2x this provider's average" isn't something a single claim can carry on its own.

    Only submitted_date is generated rather than authored, per the spec's own instruction — a small seeded PRNG (mulberry32) keyed to the current ISO week produces a deterministic-but-varied spread of claim ages (fresh, mid, near-deadline, one deliberately past its SLA deadline) that regenerates consistently within a week and shifts the next, with no reset step required.

    A validation script checks the set for internal consistency — reciprocal linked-claim pairs, valid enum values, line-item totals that actually sum to the stated charge, and the exact scenario distribution the spec calls for — deliberately scenario-aware, so a claim's own _testMeta.deliberately_missing_field tag exempts its one intentional gap from being flagged, without silencing checks anywhere else. One real type-safety catch along the way: an exhaustive form-type check's defensive fallback branch was quietly unreachable as far as TypeScript's own narrowing was concerned (never), which is correct given today's two form types — cast rather than suppressed, so it stays a real guard if a third form type is ever added.

  3. Author the three RAG corpora

    Done

    content/corpora/

    Three condensed reference documents (~500–600 words each) plus a typed manifest for the retrieval layer to consume in Phase 4: Coverage & Adjudication Policy (fully synthetic, in-house — coverage percentages, deductible logic, network rates, prior-auth rules, benefit caps), Fraud-Indicator Reference, and Regulatory Deadline Reference (ERISA's tiered deadlines plus state prompt-pay timing).

    Before writing the fraud reference, a secondhand relay from a companion planning thread claimed the five billing-fraud category names (phantom billing, upcoding, unbundling, double billing, unnecessary/substandard care) came directly from FinCEN's FIN-2026-A001 advisory. Rather than build a citable document on that relay alone, fetched the advisory and NHCAA's consumer page directly. The volume-spike red flag and NHCAA's misrepresentation framing held up; the five category names did not — FinCEN's actual advisory centers on financial red flags (shell companies, ownership-change reimbursement spikes), consistent with its real mandate as a financial-crimes regulator rather than a medical-coding one. The terms themselves are real, just grounded elsewhere (OIG enforcement, DOJ False Claims Act settlements, CMS's National Correct Coding Initiative for unbundling specifically) — corrected the attribution in the corpus, in project-spec.txt, and in the workflow-visualization diagram's node copy, all three now citing sources verified directly rather than by relay. ERISA's own tiered deadlines (72hr/15-day/30-day) were checked the same way and held up exactly as specified, against DOL/EBSA guidance and the eCFR text — with one real addition worth folding in: each non-urgent tier gets a single notified extension (up to 15 or 30 more days), which wasn't in the original spec draft.

  4. Deterministic calculation layer

    Done

    src/lib/rules/ · 31 tests, 6 files, all passing

    Five pure functions, no API calls: severity.ts (dollar band × SLA-window escalation, medical-necessity bump, breach override), sla.ts (percent-of-deadline-window math), coverage.ts (deductible/network-aware coverage math, verified against the spec's own worked example — $1,140 billed → $912 covered, exactly), action-lookup.ts (the category+confidence → action table), and status.ts. Vitest installed as the test runner.

    Planning this one surfaced a real design question worth recording: is "disputed medical necessity" — an input severity needs — something to extract from messy claim prose, or something the deterministic layer should just be handed as a clean field? Concluded it's neither exactly — it's a judgment the Pipeline's Analysis call (Phase 5) has to make by reasoning over the claim, the same way it judges the unnecessary/substandard-care fraud category. Rather than pre-bake that judgment as a boolean now, computeSeverity() takes it as an explicit parameter, sourced from _testMeta as a stand-in until Phase 5 exists — same pattern already used for the missing-info SLA-hold pause (temporary-hold.ts, explicitly marked for deletion once Phase 7 lands).

    Two structured reference datasets added alongside the rule modules — network-directory.json and member-accumulators.json — modeling something true of real claims processing: network status and deductible balance both live in separate systems (a payer's network directory, a member's benefit accumulator), never on the claim form itself, so looking them up rather than parsing them off the claim is the domain-accurate design, not a shortcut.

    Separately, added CMS-1500's real Box 19 ("Additional Claim Information") and UB-04's Box 80 ("Remarks") — genuine free-text fields on both real forms — to eight of the twenty seed claims, with realistic clinical shorthand for Phase 5 to eventually read and reason over. Deliberately included on two clean claims as well as the ambiguous/fraud ones, so the mere presence of a note is never itself a tell.

    coverage-policy.md is now generated, not hand-maintained: coverage-constants.ts is the single source of truth, and scripts/generate-coverage-policy.ts renders the citable prose document's tables from it, so the numbers Anchor cites and the numbers the calculation actually uses can't quietly drift apart.

  5. RAG retrieval layer

    Done

    src/lib/rag/ · 54 tests passing · real end-to-end smoke test against live queries

    Local, self-hosted embeddings — @huggingface/transformers running Xenova/all-MiniLM-L6-v2 — over Voyage AI, closing the one embedding-provider decision left open since the RAG mechanism was first designed. Chunking splits each corpus on its own ## headings (placed for exactly this back in Phase 2); embeddings and a plain in-memory array replace any hosted vector store, appropriately scoped to a few dozen chunks total.

    The interesting part of this phase was verifying retrieval actually works, not just that it runs. A real smoke test — genuine questions against the real corpora, not synthetic fixtures — surfaced retrieval quality problems worth working through rather than reporting as a clean first pass:

    • The chunk containing ERISA's actual tiered-deadline table ranked 5th of 6 for "what does ERISA require for pre-service claims" — the one question it was built to answer. Root cause: the chunk was built almost entirely from raw markdown table syntax (pipes, a dash separator row), which a sentence-embedding model — trained overwhelmingly on prose — embeds poorly. Fixed by embedding a flattened, plain-language version of any table (converted to one sentence per row) while still citing and displaying the original markdown.
    • That fix barely moved the ranking. The real mechanism: mean-pooled embeddings dilute a long chunk's vector toward its average content, so a short, keyword-dense chunk can systematically out-rank a longer chunk that actually contains the answer — a well-documented, genuine limitation of pure embedding search, not a bug specific to this corpus. It was compounded by an actual design mistake: every document's pre-heading "Overview" chunk was just its **Source:** provenance line — already captured structurally in manifest.ts's citation field — yet short and keyword-dense enough to out-rank real content. Dropped from the retrievable index entirely as redundant, not just re-ranked.
    • The underlying dilution problem remained, so added the standard mitigation: hybrid scoring, blending embedding similarity (70%) with a lightweight keyword-overlap signal (30%) — the industry-standard answer to exactly this weakness in pure embedding search. That recovered the ERISA tiers chunk to 2nd place (previously absent from the top 6 entirely). One query ("what counts as upcoding") still didn't fully resolve — a competing chunk happens to contain the literal word "upcoding" too — but the correct chunk was already within the top 2 there regardless, and default k was bumped to 4 for margin, which costs nothing at this corpus size.

    Left deliberately unresolved: retrieval ranking isn't perfect, and won't be tuned further at this scale — the practical backstop is that Phase 6 feeds several top-k chunks to Claude for actual answer synthesis, not just the single top-ranked one, so imperfect ranking within a small margin doesn't mean a wrong answer.

  6. Status taxonomy correction

    Done

    project-spec.txt · src/lib/rules/status.ts · workflow diagram — cross-cutting, not a numbered phase

    A review of the status taxonomy (project-spec.txt Section 7a) against the deterministic layer already built in Phase 3 surfaced a real bug in the spec itself, not just an ambiguity: the original implementation note said initial status was "derived from whether Call 1's evidence is non-empty." That rule is wrong — a complex-math claim (a detected deductible crossing) or a non-material-missing-data claim (a named missing field) both produce non-empty evidence, yet both need to stay "Submitted, no flags," since Approve is still a reachable action for each. The correct rule is category-based: fraud, ambiguous, and material-missing-data start flagged (Approve is never their eventual action); clean, complex-math, and non-material-missing-data start unflagged. status.ts was rewritten accordingly — deriveInitialStatus() now takes category (and materiality, for missing-data) instead of an evidence count.

    Working through the taxonomy also surfaced two genuine gaps, not just clarifications:

    • Denied was missing as its own status — the original 5-value list folded every closed outcome into "Resolved." Adding it back is principled, not just more status-proliferation: it passes the same test that got a 6th "Overdue" status rejected earlier (Section 5a) — does it carry real, non-redundant information? Denial carries real regulatory weight an approval doesn't (ERISA requires a "full and fair review" specifically around adverse benefit determinations), and Section 4 already singles out Deny as needing a justification. Approved stayed folded into the generic "Resolved," on purpose — there wasn't a matching asymmetric justification for splitting that one out too.
    • Additional Info Requested — a material missing-data hold was previously modeled as just a clock-pause with no visible status of its own, implying the claim would eventually get re-evaluated once the missing field arrived. But this system has no real document-intake mechanism (an explicit Non-Goal) for that field to ever actually arrive — so calling it anything other than terminal would misrepresent what the system can do. Added as its own status, reached only from "Submitted, flagged," only when a human explicitly confirms the hold is warranted rather than overriding straight to Approve — which also surfaced that Section 4's human-gate action list was missing a fifth action ("Request Additional Info") that Section 7c had already been assuming existed.

    Status is now 7 values, up from 5 — each addition justified individually against the same non-redundancy test, not accepted by default. project-spec.txt Sections 1, 4, 7a, and 9 all updated; the workflow-visualization diagram's Taxonomies and Human Gate node copy updated and republished to match; status.ts's type expanded to the full 7-value shape even though only 2 are producible by code today, so Phases 6/7 fill in an already-correct shape rather than rediscovering one.

  7. Human Gate guardrail design

    Done

    project-spec.txt Section 4a — design decision, ahead of Phase 7's code

    Speced two guardrail mechanisms for the moment a human's action is submitted through the Human Gate, ahead of Phase 7's actual build: a deterministic recommendation-mismatch check (no model call — compares the human's chosen action against the Pipeline's own recommendation, surfacing a soft "Are you sure?" confirmation citing evidence the Pipeline already produced), and a small, new model call that judges the quality of a Deny action's required justification against the claim's evidence and the retrieval layer's policy corpora, then drafts a policy-cited replacement when the human's own text is inadequate.

    Both mechanisms are deliberately soft: neither blocks a human from proceeding with their original choice, regardless of what the guardrail surfaces. That follows directly from the Core Thesis's human-gate principle, not a separate policy — a system that could override a human's Deny or Approve decision would contradict the "nothing becomes a real action without explicit human approval" premise the whole platform rests on.

    Scoped explicitly to Phase 7, not Phase 5 — both mechanisms react to a human decision made against an already-computed recommendation, not to raw claim evidence, so nothing about the Evaluation Pipeline's schema changes. One dependency worth flagging now rather than discovering mid-build: the justification-quality check needs Phase 7 to call directly into Phase 4's retrieval layer, a cross-phase wiring point.

  8. Evaluation pipeline

    Done

    src/lib/pipeline/ · Sonnet, low effort · verified live against all 20 seed claims

    The two batched calls specced back in Phase 1: Call 1 (Analysis) reads every claim — plus its linked claim for combo pairs, plus the billing provider's volume history for the spike pattern — and returns evidence and a proposed category, no tier, no recommendation. Call 2 (the isolated Confidence judge) is shown only that evidence and category, never Call 1's reasoning or the original claim again, and returns a confidence tier plus a recommendation narrative written to double as citation text for the Human Gate's mismatch-warning guardrail (Section 4a). Both calls use structured JSON output (output_config.format) rather than hoping a prompt-shaped response parses cleanly, and both stuff all three RAG corpora into context whole rather than retrieving per query — the corpora are a few pages total, and real chunked retrieval is reserved for Anchor (Phase 6), where it's the actual thing being demonstrated.

    A deterministic safety net sits between the two calls: whether a required field is actually null is a confirmed fact, not a judgment call, so missing-fields.ts checks every claim directly and overrides Call 1's category if it disagrees with a detected material gap. status.ts also gained derivePostPipelineStatus() — the auto-approval and Needs-Approval transitions are automatic, system-side outcomes of the Pipeline finishing, not a human action, so they belong in this same deterministic layer rather than waiting on Phase 7.

    The live smoke test surfaced a real reliability bug on the first two runs, not a hypothetical one: a batched call occasionally came back missing one or more claims from an otherwise well-formed, schema-valid response — structured outputs constrain each item's shape but can't express "exactly N items, covering this exact ID list," so the model can under-generate a batch without tripping any parse error. Root-caused by instrumenting both calls' raw stop_reason/usage and replaying the same inputs against a cached intermediate result rather than re-paying for Call 1 on every debug iteration. Fixed two ways: the user message now explicitly enumerates every expected claim_id and the exact count expected back, and both calls are wrapped in a completeness check that retries (up to 3 attempts) rather than trusting the first response — the second real run needed exactly one retry on Call 2 and then completed cleanly.

    End-to-end result against the real 20-claim set: 20/20 categories matched their authored ground truth, with sensible, claim-specific evidence (down to naming the exact conflicting service lines, occurrence codes, and remarks text) and correctly computed severity/status/SLA for every claim — including one claim the model itself flagged as already past its SLA deadline.

  9. Severity-on-terminal-status design

    Done

    project-spec.txt Section 7b — caught reviewing Phase 5's own results

    Reviewing the live Pipeline output surfaced a real gap: severity's deadline-proximity factor assumes a still-running decision clock, which stops being true the moment a claim is actually decided. Three auto-resolved claims in the smoke-test run displayed Moderate/High severity despite being done — nothing dishonest about that number in the single run that produced it, but the design had no answer for what happens once persistence exists (Phase 7) and a closed claim gets redisplayed later against a fresh "now."

    Resolved it by checking the actual regulation rather than assuming: ERISA's decision-deadline rule (29 CFR 2560.503-1) governs the determination only, not payment speed; state prompt-pay statutes (checked directly — North Carolina, Texas, Pennsylvania) do keep a payment clock running past approval, but none of them reset a fresh timer at the approval date — all run from claim receipt. Since this system explicitly doesn't simulate reimbursement at all (an existing Non-Goal), there's no honest data to keep escalating severity against post-decision — so severity resets to Low on Resolved or Denied, rather than freezing at its pre-decision value. Additional Info Requested is the deliberate exception: it was never actually decided, just stuck, so its severity stays frozen at the hold's start value — already the existing SLA-hold mechanism's natural behavior. Escalated and Needs Approval, still awaiting a real decision, are untouched.

    Spec-only for now, same as the Human Gate guardrail design above — the code is Phase 7's, since that's when a real decision timestamp first exists to freeze severity against. Phase 5's own output isn't wrong today; this closes a gap that would only bite once persistence lands.

  10. Interactive router & Anchor

    Done

    src/lib/router/ · Sonnet, low effort · verified live against an adversarial question set

    Real Claude tool-use across the four tools from Section 1: Lookup, Analysis, Recommendation, Reference Lookup. Two of the three planning questions carried over from Phase 5 resolved the same way: same model/effort tier (routing among four well-separated tools is a narrower problem than the Pipeline's five-way category call, which already proved reliable here), and one-shot rather than multi-turn — no chat UI exists yet to justify the token-cost growth and state-management complexity of real conversation history, so the round-trip takes an optional prior-turns shape without actually using it yet.

    The third — how the Router handles an ambiguous, broad query like "show me problem claims" — had sat in Open Items since Section 1 was first written. Resolved by extending Lookup to accept a structured filter (status/severity/category) alongside a specific claim ID, so a broad query is an ordinary Lookup call rather than a special case outside the four-tool structure, plus a small house table mapping common ambiguous phrases to a default filter. The response pattern is deliberate: always show best-guess results now and state the interpretation plus a named alternative in the same answer — never a silent guess, never a blocking clarifying question before showing anything.

    Analysis and Recommendation default to re-surfacing the already-computed Pipeline result for a claim — free, instant, code-only — rather than paying for a new call every time an adjuster asks about a claim the Pipeline already evaluated. An explicit "re-check" request reruns Call 1 + Call 2 fresh for just that one claim, reusing Phase 5's own functions directly (reconcileCategory and buildClaimResult were pulled out of orchestrator.ts as standalone exports for exactly this, rather than duplicating the merge logic).

    A ten-question adversarial set — not happy path — probed the three failure modes Section 1 names explicitly, plus the ambiguous-query fallback and a genuinely out-of-scope request ("deny this claim"). One real bug surfaced on the first live run: a question that reasonably needed two tools in sequence (claim facts, then a policy fact) had its second tool call silently dropped, because the round-trip only handled a single dispatch round. Root cause was a code gap, not a model mistake — fixed as a bounded loop (up to 4 rounds) rather than assuming every question resolves in exactly one tool call. Rerun clean: correct tool chosen in every case, including holding onto the claim actually named in a question rather than defaulting to the claim in view, correctly declining to fabricate a prior-authorization answer when neither the claim data nor its analysis supported one, and refusing the out-of-scope denial request while naming what it could actually do instead.

    Also gave Phase 4's real chunked retrieval layer its first actual caller — the Pipeline (Phase 5) deliberately uses full-context stuffing instead, so Reference Lookup is where retrieval finally gets exercised for real, not just smoke-tested in isolation.

  11. Human gate & persistence

    Done

    src/lib/humangate/ · src/lib/persistence/ · real jsdom tests · verified live

    Three scope questions settled before writing anything: the guardrail check needs a live model call, so does that mean standing up the first real app/api/ route? No — a plain server-side function now, tested headlessly like everything else; the actual HTTP wrapper waits for Phase 8, when a browser genuinely needs to call it. localStorage only exists in a browser — real jsdom-backed tests instead of a hand-rolled in-memory fake, matching this project's running preference for testing the real thing. And the real per-ISO-week Pipeline cache: build it now, since the Pipeline is provably nondeterministic run-to-run (directly observed in Phase 5/6 testing) and the audit log needs a stable snapshot to log against — an in-memory, ISO-week-keyed cache, correct within one process's lifetime; upgrading to Next.js's Data Cache for cross-invocation durability on Vercel is a flagged, deliberate follow-up for when this is actually wired into app/.

    Both Section 4a guardrails built: the deterministic recommendation-mismatch check (no model call — a claim's chosen action compared against the Pipeline's own recommendation), and the RAG-grounded justification-quality check, genuinely retrieving against the corpora via retrieve() rather than full-context stuffing. A late realization during planning simplified Section 7b's severity rule considerably: earlier framing assumed a stored decision timestamp was needed to "freeze" severity on a closed claim — it isn't. Once status is Resolved or Denied, severity is just always Low; no time-dependence, no state to track, a status check ahead of the existing calculation.

    Also corrected a real architectural inconsistency while touching this code: temporary-hold.ts's SLA-clock-pause logic was reading claim._testMeta directly — the authoring answer-key field explicitly meant to never touch real system logic (Phase 5 established this rule for the Pipeline; this file had quietly broken it since Phase 3). Swapped for missing-fields.ts's deterministic scanner, which checks the actual data instead of the test metadata that happens to correlate with it.

    Section 6's coverage math got its first real caller — computeClaimCoverage(), wiring Phase 3's computeCoverage() to real network-directory and member-accumulator lookups. That surfaced a genuine bug on the first pass: CMS-1500's box24f_charge turned out to be a per-unit rate (needing multiplication by box24g_units), while UB-04's box47_total_charge is already a line total — mixing them up understated one claim's total by $420. Caught by cross-checking the computed total against each claim's own authored total_charge across all 20 claims, now locked in as a regression test.

    Live verification (Sonnet, low effort, same as Phases 5–6): a flippant justification ("Eat my shorts") was correctly rejected with a policy-cited replacement — Section 4a's own worked example, now a real, passing case. More telling: a vague-but-serious-sounding justification ("found a discrepancy the automated evidence missed") was rejected too, for being unverifiable rather than for tone. And in one case where the chosen action actually matched the recommendation — no mismatch — the justification check still caught that the adjuster's stated reason named the wrong fraud category against the claim's real evidence, and said so specifically rather than passing it through because the action itself looked right.

  12. Human Gate extension — structured denial, reversible actions, recoupment

    Done

    src/lib/humangate/ · src/lib/rules/ · test suite extended, all green

    Deny's justification split from a single free-text field into four structured ones — specific reason and the plan/policy provision cited (both required), plus the internal rule or clinical standard applied and what might reverse the decision (both optional) — so the justification-quality guardrail can point at exactly which field falls short instead of grading one undifferentiated paragraph. Still one batched model call evaluating all four together, not four separate calls. A free-form audit note was added alongside it, for attaching context without taking a status-changing action at all.

    A genuinely new terminal status: Recoupment Requested, reached only from Resolved. Modeled deliberately as forward-only, not a reversal — Approve stays permanent, since unwinding a real payment has actual legal weight this system doesn't simulate. Paired with three real reversible actions — undoing a request-for-info, an escalation, or a denial — each of which looks up its own matching entry in that claim's audit log and reverts to that entry's prior status, rather than a fixed target the way the original five actions are. All four require a non-blank note, validated but not judged — there's no fresh recommendation to weigh a reversal against the way there is for a first-time Deny. Severity gained a matching fixed case: Recoupment Requested is always High, the mirror image of Resolved/Denied's fixed Low — same reasoning (no real timeline left to compute against) but the opposite value, since a claim under active clawback is exactly the kind of exception a severity-sorted worklist exists to surface. The workflow-visualization diagram was updated to match: eight lifecycle statuses, the new severity override, and a dedicated post-terminal-actions node.

  13. Visual design system

    Done

    Figma · token-driven · three styles × light/dark

    Five initial style directions narrowed to three, each carrying a genuinely different point of view rather than a palette swap: Ledger (dense, tabular, high information density for a high-volume queue), Clinical (serif, precision-first, reads like a clinical record), and Field (warmer, more approachable, for a less adversarial read of the same data). Each ships in light and dark — six combinations total — driven end to end by a token architecture rather than six hand-maintained copies: a single Primitives layer of raw values, a six-mode Color collection (one mode per style/brightness pair), and a three-mode Type & Shape collection for font and radius conventions per style. Every screen recolors and refonts from those bound modes; nothing is hardcoded per instance.

    Contrast held to WCAG AAA (7:1) throughout, checked computationally rather than eyeballed — caught and fixed three real failures (accent text against its own ink color dropping as low as 4.77:1 in Clinical light and 6.98:1 in Ledger dark) by retuning the underlying primitives rather than the components using them, so the fix propagated everywhere at once.

    The Claims Card carries a three-way toggle — Quick View, All Claim Fields, Audit Log — with the "all fields" view grounded directly in the real schema rather than a mocked-up subset: genuine CMS-1500 and UB-04 box numbers, itemized service/revenue lines, the same field names the deterministic layer actually reasons over. Guardrail states from the Human Gate design are fully surfaced: a soft "[Action] anyway" confirmation naming the Pipeline's actual recommendation when a chosen action doesn't match it, and Deny's four-field justification form with a real accept/edit/submit-as-is/cancel flow when the quality check flags something. A single "Reverse denial decision" / "Request recoupment" affordance replaces the four-action row once a claim reaches a terminal state, matching the Human Gate extension above — built and verified across all six style/mode combinations.

    A legend system answers the taxonomy questions a reader without claims-adjudication background would actually have: a small info icon next to Status and Severity in every dashboard's table header, and next to AI Confidence on every claim card's badge row, opening reference panels that plain-language every status, severity band, and confidence tier. An appearance-settings panel exposes the style and light/dark choice directly, rather than leaving it to a URL param or a build flag. The Anchor Assistant panel — input, grounded response, a bulk-action confirmation pattern ("Approve all 14 claims"), and citation mini-cards back to the claim in question — carries suggested-question pills seeded with claims-adjudication-specific prompts, so the assistant's value is legible on sight rather than requiring a reader to already know what to ask.

  22. Phase 12 — Kimi / provider flexibility

    Done

    src/lib/pipeline/model-client.ts · scripts/compare-providers.ts · Pipeline routed to Kimi in production

    Motivated by two real things this build surfaced on its own: Kimi's meaningfully lower cost, and the Pipeline's own observed run-to-run classification inconsistency, which raised a fair, testable question — does a different model handle the same batched-reasoning task more consistently, given the same complete information? Architecture first: model-client.ts consolidates the Pipeline's two calls behind one shared callModel(), provider selected by a parameter threaded through runAnalysis/runConfidence rather than hardcoded per file. Anchor's tool-use loop and the Deny justification-quality check were deliberately left out of this consolidation — their request shapes differ enough between providers that forcing a shared interface would be a leaky abstraction, not a real unification. Kimi is routed through the OpenAI SDK against Moonshot's own OpenAI-compatible endpoint specifically, not its undocumented Anthropic-compatible surface — sidestepping an unconfirmed structured-output compatibility question entirely rather than testing into it.

    Getting Kimi actually running surfaced three real infrastructure bugs, none of them subtle once found. K2.6's own native reasoning mode breaks structured JSON output outright — floods the response with a long run of near-blank whitespace and never completes the object, confirmed reproducible twice, including after the prompt had changed substantially between the two checks. Running with reasoning explicitly disabled is what actually works. Separately, the OpenAI SDK's own client-level timeout didn't reliably fire — one request ran 13+ minutes past its configured bound with no error at all — replaced with a manually enforced Promise.race timeout; a stray, uncleared timer from that same fix then kept the process alive for minutes after the real work had already finished, fixed by clearing it once the race actually settles. And Moonshot's own Tier-0 new-account rate limit (1.5M tokens/day) got hit purely from testing volume, resolved with a real top-up crossing the $10 cumulative-recharge threshold that unlocks Tier 1's unlimited daily cap.

    Comparison ran through a real multi-pass harness (compare-providers.ts), not a single trusted run — the same fixed, ISO-week-seeded 20-claim set both providers see identically, repeated passes per configuration, tracking confidence tier and the deterministic status the Pipeline actually assigns alongside raw category accuracy. That last piece produced the phase's most useful methodological finding: raw accuracy treats every miscategorized claim as equally bad, but the deterministic layer doesn't. A wrong category paired with a cautious confidence tier still reaches a human; only a wrong "clean" call paired with a confident tier resolves automatically, with nobody ever reviewing it. Tracking that specific outcome — a "silent miss" — turned out to be more decision-relevant than the accuracy number on its own. The harness also caught a bug in its own grading, not just in the model calls: one claim's ground-truth label described which authored "combo" scenario it belonged to, not the category the Pipeline should assign to that specific claim — its own authored note said so explicitly — and grading against the raw label had been silently under-scoring both providers by up to a full point for the entire testing history until this was caught and fixed.

    Prompt tuning produced a real, mixed result, not a clean success story. Targeted few-shot examples for two fraud sub-types Kimi was systematically softening toward clean/ambiguous measurably worked — both recovered from a majority-wrong pattern to a majority-right one. A dedicated example built for a separate complex-math claim never fixed its target, confirming this kind of tuning has to be verified against repeated results, not assumed to work just because the mechanism is sound in principle. An explicit reasoning field, forced ahead of the category decision in the schema itself, was a clean win for Claude — which already runs adaptive thinking privately and mostly just needed a place to state the conclusion — but neutral-to-mildly-negative for Kimi, which has no private reasoning phase of its own, making the field its only reasoning step rather than a summary of one already settled. Kept for Claude, dropped for Kimi.

    Final numbers, confirmed across two independent matched-prompt batches each: Claude averaged 18.4/20 (92%) category accuracy, a 5% silent-miss rate, and completed cleanly on roughly 4 of 5 runs. Kimi averaged 16.3/20 (82%), a 13% silent-miss rate, and completed cleanly on every single run tested. Real, opposite trade-offs, not a win for either side outright — Claude is more accurate and safer when it finishes; Kimi finishes more consistently. The Pipeline's real cache (pipeline/cache.ts) and Anchor's own recheck path are now both routed to Kimi in production, a cost-driven decision for a public portfolio prototype with no real patients, providers, or dollars on the line — documented explicitly, in code and here, as a different call than an actual production system would be permitted to make, given project-spec.txt's own Non-Goals already rule out exactly the kind of real-world stakes an 8-point safety gap would need to be weighed against.

    A standalone data-visualization page, built the same day and shared as its own artifact, covers the full comparison — the accuracy arc across every prompt iteration tested, the reliability gap, and the silent-miss breakdown for both providers side by side.

A first implementation — a chain of nested setTimeout calls — tested correctly in isolation, including under React StrictMode and through the real hydration path, and yet stayed frozen on the very first fact through a genuine ~90-second cold Pipeline run in production. The actual cause: a Suspense fallback held open that long during a streamed SSR response is exactly the scenario most likely to have its DOM node torn down and recreated mid-wait by the browser or an intermediary proxy, silently resetting an in-memory timer chain each time. Rebuilt to derive the current fact from real elapsed wall-clock time, anchored in sessionStorage rather than kept in memory — self-correcting no matter how many times that happens, verified with a test that specifically simulates the remount rather than just the happy path.

  58. Pre-warming the weekly Pipeline cache

    Done

    vercel.json

    The per-ISO-week Pipeline cache means only the first visitor after a weekly rollover pays for a live run — everyone else that week gets an instant cached result. Closed the remaining gap with a daily Vercel Cron hitting /api/pipeline at 00:05 UTC: cheap, since every call after the first real trigger that week is just a cache hit, and it reuses the exact same code path a real visitor's request already takes. A known, accepted limit rather than a full guarantee: a visitor arriving earlier the same day the ISO week rolls over, before that day's cron fires, could still hit one cold run a week — judged an acceptable tradeoff for a portfolio site rather than paying for sub-daily cron frequency.

  59. Chunk-count tuning, and removing the Call1/Call2 barrier

    Done

    orchestrator.ts — live timing comparisons, then a real concurrency fix

    A live visitor report of a slow cold load led to measuring chunk count directly rather than guessing: 6, 8, 9 (twice), 10, and 12 chunks against the full 132-claim set, using a diagnostic script built for exactly this. 9 chunks (size 14) was the clear, twice-confirmed winner — the only count tested twice specifically to rule out a lucky run — and is now the default, replacing the prior default of 22.

    A second, more structural fix followed: every chunk's own Call 2 previously had to wait for every chunk's Call 1 to finish first, a global barrier that erased almost all of the time a fast chunk had actually saved. Each chunk now runs its own complete Call 1 → Call 2 sequence independently, verified live via timestamped logs showing the first Call 2 result landing while other chunks were still on Call 1. The real trade-off: Call 2 no longer gets rebalanced across chunks by each claim's confirmed category, since that rebalancing needed every chunk's Call 1 result at once — the same thing this removes. A separate live test of switching the corpus to real RAG retrieval (rather than full-context stuffing) in these same two calls found no time savings, possibly the opposite, and was not pursued.

  60. Progressive Pipeline rendering, and the Figma-specced loading toasters

    Done

    DashboardLoader.tsx · progress.ts · LoadingToast.tsx · a client-hydration bug and two Anchor pill bugs

    The homepage no longer sits behind one all-or-nothing wait for the full Pipeline run. Each chunk's merge into a finished, render-ready result now fires a callback the moment it's ready — the same independence the Call1/Call2 barrier removal made possible — which a new in-memory per-week tracker picks up without touching the existing cache's own key. A polled endpoint exposes that partial state, and a new client-side loader renders a growing worklist as chunks land instead of one blocking screen, falling back to the existing branded loading experience (moved into components/ so it could be reused directly) until the first real chunk arrives.

    Alongside this, two blue/green toaster notifications specified in Figma — "still loading" and "pipeline complete" — were built with their real animation timing (a genuine height transition that pushes the rest of the page down, not an overlay) and wired to this same real state, replacing an earlier timer-based stand-in used to review the animation before the real signal existed.

    Three real bugs surfaced live during this pass, not in testing: rendering the loading screen from inside a real client-hydrated tree (rather than its old life as a Suspense fallback that was simply discarded, never reconciled) produced a genuine hydration mismatch, since the server and client each picked a different random fact order — fixed by rendering a fixed order on mount and shuffling only afterward. Separately, Anchor's suggested-prompt pills started reshuffling on every chunk update, traced to an unmemoized array being handed to an effect that shouldn't have been reactive to it at all; fixing that then surfaced a second issue — the pills also needed an explicit redraw after a real question, which had previously only worked by the same accident that caused the first bug.

  61. Fixed table/card headers, viewport-safe claim cards, and a new footer

    Done

    ClaimsTable.tsx · Modal.module.css · Footer.tsx — two real max-height bugs, not one

    Three UI fixes. The Claims List title, search bar, and bulk-action bar now stay fixed above the table while only the table and pagination scroll beneath them — previously the whole block scrolled together as one unit. Claim card overlays are now bounded to the viewport and scroll internally instead of forcing the whole fixed-viewport page to scroll, which used to make the table and Anchor panel look cut off (both are sized to exactly fill that viewport and were never meant to scroll as a block). A card's basic info and view toggle now stay fixed at the top; everything below the divider under the toggle — tab content and the action buttons — scrolls within the card itself.

    Getting the card's height bound right took two real, distinct fixes. First: a percentage max-height on the card had no definite parent height to resolve against, so it was silently ignored — overflow: hidden was just hard-cropping the card instead of ever letting it scroll. Fixed by making the modal layer a real flex container, which flexbox can correctly constrain without needing a percentage height at all. Second, live-tested right after: a 100vh-based max-height measured from the wrong origin, since the layer's absolute positioning is relative to the table region, which itself starts well below the true viewport top (under the masthead and stat tiles) — switched to 100% so it resolves against that region's own actual height instead, which does end at the real viewport bottom.

    New: a fixed footer — ClaimsDock logo, copyright, links to the portfolio site, LinkedIn, and the system diagram — sized off one shared height/gap token pair in tokens.css, so every internally-scrolling region (table, Anchor history, claim-card body) reserves the same clearance above it without hardcoding the number three times. Also capped Anchor's panel at 690px on very large viewports, where 30% of the screen was more than the panel needed.

  62. Anchor can select and deselect claims — a real grounding failure found and fixed along the way

    Done

    select_claims · deselect_claims · a false-claim bug worse than the feature it shipped with

    Two new Router tools, select_claims and deselect_claims, reuse lookup_claim's existing filter matching rather than new logic — they check or uncheck matching claims in the Claims List so the adjuster can run a real bulk action from there. Anchor never performs the action itself; the human gate stays exactly where it was.

    The first live test surfaced something more serious than a missing feature: asked to deselect a real selection, Anchor confidently replied that it had — with a specific, plausible-sounding count — with no tool call behind it at all. It had read the existing "Selected claims" context note (built for informational questions like "tell me about these") and used its count to generate a confident confirmation, never recognizing that knowing the current selection isn't the same as changing it. Asked to deselect "the second half" of a selection — a request the tool genuinely can't express, since it only understands structured filters, never position — it went further: fabricated a fake deselection count, falsely claimed the list was empty, and invented nine specific claim IDs that were never real tool output. Fixed with an explicit prompt rule distinguishing "information to read" from "proof a change happened," and honest handling for requests the filter can't express — say so, never approximate with an invented filter or invented IDs.

    The same false-claim pattern recurred in a narrower case: a standalone deselect request asked immediately after an answer that had itself just narrated a selection change. The model was treating its own recent wording as evidence the new request was already handled — extending the system prompt's existing "Prior turn" rule (already required for read questions, after an identical bug found live in Phase 13) to selection actions closed this.

    A separate, genuine client-side bug surfaced once the prompt-level issues were fixed: a combined "clear this selection and select claims that need approval" request correctly called both tools, but applying them as two independent state updates meant deselect's own clear-everything branch always won outright, silently discarding whatever select had just set in the same exchange. Fixed by folding every select/deselect call in an exchange, in the order the model actually made them, into one final selection applied as a single update — not two updates that could step on each other.

    Three smaller phrase-mapping misfires rounded out testing: "claims that need to be escalated" and "claims that need additional info" were both falling back to a broad pre-existing "still active" interpretation instead of the specific recommended_action they name; "claims that need approval" was doing the same instead of mapping to its own literal status value. All three fixed with direct, unambiguous mappings alongside the existing "recommended action is Deny" precedent they mirror.

    Testing infrastructure improved alongside the feature: smoke-test-router.ts gained a way to simulate a real prior checkbox selection and a real prior turn per test case — neither existed before, which is exactly why the failure modes above were never exercised until they broke live — plus an --only=<substring> flag for a targeted regression run without re-paying for the full adversarial set every time. Its own claim-index build was also found silently defaulting to Claude on every run regardless of which provider was actually being tested, inconsistent with the app's own Kimi-first cost discipline — switched to always use Kimi for that setup step.

How this got planned

  • Spec first, code second

    Every architectural question below got resolved in the spec document before any file was written — the two-call pipeline, the retrieval mechanism, the persistence split. Nothing here got decided implicitly while writing code.

  • Decisions get dated and inlined, not left implicit

    Each resolved question was written into project-spec.txt as an "implementation note," dated, next to the section it amends — so the reasoning stays attached to the rule instead of living only in a chat transcript.

  • Real RAG, correctly scoped

    Chunked embeddings and an in-memory similarity search over a small, purpose-written corpus — not a hosted vector database the project doesn't need, and not full-context stuffing that would skip demonstrating retrieval at all.

  • Calculations stay calculations

    Severity, SLA math, and coverage math were already specified as deterministic — the pipeline redesign made sure the code matches that on purpose, rather than letting a model quietly re-absorb work that was designed to be a lookup.

  • Open questions stay open, on purpose

    Embedding provider and 100+ claim batching strategy were both deliberately left undecided rather than forced early — real unknowns get flagged and revisited at the phase they actually matter, not guessed at now.
